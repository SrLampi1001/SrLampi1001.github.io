# 01 — Architecture

This document describes the conceptual architecture of the SrLampi1001
Portfolio Platform. It is intentionally high-level: implementation details live
in the dedicated documents for each subsystem.

---

## 1. The platform in one paragraph

The portfolio is a **static, automatically maintained index** of every public
software project authored by SrLampi1001. It is generated by an Astro
application that lives in this repository and is published through GitHub
Pages. The portfolio itself runs no server-side code; every project listed in
it remains independently understandable, buildable, and deployable on whatever
technology stack its authors chose.

---

## 2. The three layers

The platform is divided into three conceptual layers:

```
┌──────────────────────────────────────────────────────────┐
│                  PORTFOLIO INDEX                         │
│                                                          │
│  SrLampi1001.github.io                                   │
│  Astro + TypeScript                                      │
│  Static generation                                       │
│  Project discovery / filtering / presentation            │
└─────────────────────────┬────────────────────────────────┘
                          │
                          │  Reads project metadata
                          ▼
┌──────────────────────────────────────────────────────────┐
│                  PROJECT REPOSITORIES                    │
│                                                          │
│  React / Angular / Astro / Docusaurus                    │
│  FastAPI / Node.js / .NET                               │
│  Python / CLI / Fundamentals                             │
│  Monorepos / Collections                                 │
│                                                          │
│  Each repo ships a project.yml that the portfolio reads │
└─────────────────────────┬────────────────────────────────┘
                          │
                          │  Optional deployments
                          ▼
┌──────────────────────────────────────────────────────────┐
│                 EXTERNAL RUNTIMES                        │
│                                                          │
│  GitHub Pages                                            │
│  Cloudflare Pages / Workers                              │
│  Vercel                                                  │
│  Render                                                  │
│  Supabase                                                 │
│  Pyodide / WebAssembly                                    │
└──────────────────────────────────────────────────────────┘
```

The portfolio never assumes that a project uses Astro, GitHub Pages, or any
particular language. It only consumes the project's `project.yml` plus a small
amount of GitHub-derived repository metadata, and renders the rest as static
content.

## 3. Data flow

End-to-end flow of a single project from creation to publication in the
portfolio:

```
Developer creates project
        │
        ▼
Adds project.yml
        │
        ▼
Pushes repository
        │
        ▼
Project CI/CD runs
        │
        ▼
Project is deployed (optional)
        │
        ▼
Portfolio discovery workflow runs
        │
        ▼
Astro fetches project.yml + GitHub metadata
        │
        ▼
Astro builds static pages
        │
        ▼
GitHub Pages deployment
        │
        ▼
https://SrLampi1001.github.io
```

The goal is that **creating a valid `project.yml` is enough** for the
portfolio to understand the project. Everything else is automatic.

## 4. Separation of responsibilities

Each layer is responsible for its own concerns and never crosses into the
responsibilities of another layer.

### 4.1 Portfolio

Responsible for:

- discovery (finding `project.yml` files across repositories);
- indexing (parsing and validating project metadata);
- presentation (cards, pages, categories, tags, search, filters);
- metadata interpretation (mapping the contract onto UI);
- demo UI (the wrappers around Pyodide, terminal emulators, API explorers).

### 4.2 Individual project

Responsible for:

- source code;
- tests;
- architecture;
- dependencies;
- internal documentation;
- its own CI/CD;
- its own deployment configuration.

### 4.3 Hosting provider

Responsible for:

- running the application;
- exposing deployment endpoints;
- infrastructure.

### 4.4 GitHub

Responsible for:

- source control;
- repository metadata (creation date, last commit, branches);
- CI/CD integration (`repository_dispatch`, `workflow_run`);
- Pages hosting.

## 5. Metadata sources

Information about a project is split between three sources. The portfolio
combines them instead of duplicating them.

| Source | Owns | Examples |
|--------|------|----------|
| **`project.yml`** | Semantic project metadata | name, description, categories, tags, type, technologies, demo config, deployment config, presentation preferences |
| **Git / GitHub** | Repository metadata | repo existence, commit history, latest update, repo URL, repo creation date, branches, commit activity |
| **Deployment provider** | Runtime state | whether a deployment exists, deployment URL, runtime status |

**Implication**: things like `created_at` and `updated_at` should be derived
from GitHub where possible rather than stored in `project.yml`. Only project-
level, semantic concepts live in the YAML file.

## 6. Project types

The `type` property is the project's primary nature. The initial supported
types are:

```text
frontend
backend
application
fundamentals
collection
```

A project can also declare multiple **components** when it does not fit a
single category:

```yaml
type: application

components:
  frontend: true
  backend: true
  database: true
```

This avoids forcing complex full-stack projects into a misleading single label.

---

## 7. Deployment is optional and independent

Deployment and presentation in the portfolio are **decoupled**. A project can:

- have a deployment and no embedded demo (e.g. a public REST API);
- have a demo and no separate deployment (e.g. a Pyodide Python script);
- have both;
- have neither (purely a source-code reference).

See [02 — The `project.yml` Contract](./02-project-yml-contract.md) and
[04 — Deployment & GitHub Pages](./04-deployment.md) for details.

---

## 8. Full-stack scenario

A full-stack project typically has independently deployed frontend and
backend components:

```
                GitHub Pages
                     │
                     │ HTTPS
                     ▼
             Frontend application
                     │
                     │ REST / API
                     ▼
               Backend service
                     │
                     ▼
                  Database
```

The portfolio does **not** need to know the internal architecture of either
side. It only needs the resulting deployment metadata:

```yaml
deployment:
  frontend:
    type: github-pages

  backend:
    type: cloudflare-worker
    url: https://api.example.com
```

## 10. Future extensions

The architecture deliberately leaves room for future functionality that does
not change the fundamental contract:

- automatic project health checks;
- deployment status indicators;
- GitHub repository statistics;
- commit activity widgets;
- automated screenshots;
- API documentation generators;
- architecture diagrams;
- interactive API explorers;
- more browser-executable languages;
- additional WebAssembly runtimes;
- project dependency visualization;
- automated demo availability checks;
- project versioning and release information;
- CI/CD status badges.

Each of these is implemented as an *additional* source layer that augments the
existing `project.yml` + GitHub + deployment triple, never as a replacement
for it.
